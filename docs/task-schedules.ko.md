# 작업 예약

작업 생성 화면에서 즉시 실행, 1회 예약, 매일, 매주를 선택합니다. 예약은 작업 내용·모델·범위·제한 설정을 저장하고, 실행 시각마다 새 작업을 생성합니다. 기존 작업의 동시 실행 제한과 대기열을 그대로 사용합니다.

작업 목록의 **예약 관리**에서 일정과 작업 이름·설명·목표를 수정하거나 일시정지·재개·취소할 수 있습니다. 실행 이력에는 생성된 작업 링크와 건너뜀/생성 실패 결과가 표시됩니다(최근 100회). 취소는 이후 예약만 중지하고 이미 생성된 작업에는 영향을 주지 않습니다. 과거의 1회 예약을 다시 사용하려면 수정 화면에서 미래 날짜와 활성 상태를 지정합니다.

## 시간대

Docker Compose의 `TZ` 기본값은 `Asia/Seoul`입니다.

```yaml
services:
  artex:
    environment:
      TZ: Asia/Seoul
```

시스템 설정의 표시 언어 바로 아래에서 서버 시간대(읽기 전용), 예약 기본 시간대, 현재 적용 시간대와 출처를 확인할 수 있습니다. 우선순위는 유효한 시스템 override → 유효한 TZ → Asia/Seoul입니다. override를 비우면 환경변수를 다시 사용합니다. `Local`이나 파일 경로 대신 `Asia/Seoul`, `Europe/London`, `UTC` 같은 IANA 이름을 사용하세요.

웹에는 TZ만 명시적으로 노출하며, 전체 환경변수를 반환하지 않습니다. 유효하지 않은 TZ는 화면에서 원래 값과 실제 적용 기본값을 확인할 수 있습니다. 시간대 데이터는 Go 바이너리에 포함됩니다.

각 예약은 생성 시점의 시간대를 보관합니다. 시스템 기본값을 바꿔도 기존 예약은 바뀌지 않으며, 예약 수정 화면에서 개별 변경할 수 있습니다. 매일·매주는 해당 지역의 시계를 기준으로 계산합니다. 서머타임 전환으로 시각이 사라지는 날은 건너뛰고, 두 번 나타나는 시각은 첫 번째만 실행합니다. 존재하지 않는 시각의 1회 예약은 거부합니다.

## 실행 및 복구 정책

- 서버는 약 5초마다 확인하므로 예약 시각과 실제 실행 시작에는 지연이 생길 수 있습니다. 실행 슬롯이 없으면 기존 대기열에서 기다립니다.
- 이전 회차의 작업이 미완료(대기·일시정지 포함)이면 다음 회차는 건너뜁니다.
- 서버 시작 시 지난 1회 예약은 한 번 생성합니다. 지난 반복 일정은 밀린 작업을 생성하지 않고 건너뜀 이력을 남긴 뒤 다음 미래 일정부터 실행합니다.
- 일정 선점, 작업 생성, bootstrap 대기열, 이력, 다음 실행 시각을 같은 PostgreSQL 트랜잭션에 저장합니다. 회차별 유일성 제약으로 중복 작업 생성을 막습니다.
- 생성된 작업은 기존 작업 복구 경로를 사용합니다. 프로세스 중단 전후의 개별 모델/도구 호출에 대해 exactly-once 실행을 보장하는 기능은 아닙니다.
- 생성 실패 회차는 `failed`로 기록하고 자동 재시도하지 않습니다. 다음 반복 회차는 계속 진행합니다.
- 수정과 실행이 겹치면 먼저 DB에 반영된 작업이 기준입니다. 오래된 revision으로 수정하면 HTTP 409가 반환되므로 목록을 새로 읽어 수정합니다.
- 취소는 soft delete로 기록해 이미 생성된 작업의 복구 정보를 보존합니다.

## API

기존 로그인 인증을 사용하는 다음 API를 추가합니다.

- `GET/POST /api/task-schedules`
- `PUT/DELETE /api/task-schedules/{id}`
- `GET /api/task-schedules/{id}/runs`
- `POST /api/task-schedules/preview`
- `GET/PUT /api/settings`: `timezone_override` 쓰기, `timezone_env`, `timezone_effective`, `timezone_source` 읽기

일정은 `spec`의 `kind`, `date`(once), `time`(HH:mm), `weekday`(weekly, 일요일=0), `timezone`으로 표현합니다. 작업 생성 payload는 기존 `POST /api/tasks` 형식을 `task` 아래에 넣습니다. 수정 시 `revision`을 함께 보내 동시 변경을 감지할 수 있습니다. 일정 또는 enabled만 수정하면 저장된 작업 설정은 보존됩니다.

## 배포 경계

스키마는 기존 방식대로 새 바이너리 시작 시 적용되는 추가 테이블 두 개(`task_schedules`, `task_schedule_runs`)입니다. 개발·검증 중에는 별도의 PostgreSQL 테스트 인스턴스만 사용했습니다. 운영 DB 반영이나 실행 중인 ARTEX 컨테이너 교체는 이 변경의 검증에 포함되지 않습니다. 배포 전에 DB 백업과 적용 시점을 별도로 정해야 합니다.
